# Проект мультиплеера

**Статус:** черновик архитектуры для обсуждения. Документ уточняет [этап 5 roadmap](roadmap.md) и предлагает ответ на вопрос 89, но не заменяет принятые решения в [GDD](gdd/07_online.md).

## 1. Цель и границы

Нужен PvE-кооператив на 2–4 игроков. У каждого игрока собственный отряд из трёх героев, активен один герой. Игроки вместе проходят один забег, получают персональный лут и сохраняют прогресс на сервере.

Уже принято в GDD:

- игра всегда онлайн, офлайн-профиля нет;
- EOS Connect связывает платформенные аккаунты, EOS Lobby используется для лобби и приглашений, EOS P2P и relay доставляют игровой трафик;
- один из игроков — хост, выделенный сервер боя не используется;
- Rust API хранит профили и обрабатывает результат забега, но не участвует в покадровой симуляции;
- обычные ресурсы и лут не защищаются серверным античитом; сервер строго проверяет только донатные операции.

В первый сетевой релиз **не входят**: PvP, подключение в середине забега, перенос хоста, выделенные игровые серверы, общий лут и независимое нахождение игроков в разных комнатах. Это ограничения первой версии, а не невозможность добавить их позже.

## 2. Основное архитектурное решение

Использовать **авторитетного хоста с командами клиентов, предсказанием собственного героя и интерполяцией остальных**.

Хост — единственный владелец игрового состояния. Он один выполняет:

- движение и коллизии всех героев;
- действия отрядов: атаку, скилл, рывок и свап;
- AI, навигацию и выбор целей врагов;
- хитбоксы, `HitRegistry`, `DamageSystem`, статусы и смерть;
- игровой RNG, спавн, комнаты, лут, воскрешение и итог забега.

Клиент:

- читает локальный `InputMap` и отправляет команды;
- предсказывает только собственный отряд;
- получает снапшоты и исправляет предсказание;
- показывает чужих героев, врагов и эффекты, но не изменяет их игровое состояние;
- не присылает хосту позицию, нанесённый урон, выпавший лут или результат боя.

Rust API не становится вторым авторитетом забега. Он аутентифицирует игрока и идемпотентно сохраняет выданный ему итог.

### Почему не другие модели

| Модель | Решение | Причина |
|---|---|---|
| Авторитетный клиент | Не использовать | Клиент мог бы сам назначать урон, позицию и лут; состояния игроков разошлись бы |
| Deterministic lockstep | Не использовать | `CharacterBody2D`, `Area2D`, навигация и порядок физики Godot не гарантируют побитовую одинаковость на разных платформах; задержка ввода была бы у всех |
| Rollback всего мира | Не использовать в MVP | Дорого и сложно для AI, навигации, статусов, хитбоксов и четырёх отрядов; хост не откатывает прошлое |
| Выделенный сервер боя | Не использовать | Противоречит принятой схеме EOS P2P и увеличивает стоимость и объём инфраструктуры |
| Авторитетный хост | **Принять как основу** | Соответствует GDD, текущему фиксотактовому бою и модели «друзья в коопе» |

Цена решения: у хоста нет сетевой задержки, а его отключение завершает сетевой забег в MVP. Перенос хоста требует отдельного дизайна и не должен неявно появиться в реализации.

## 3. Состав runtime

### 3.1 Общая схема

```text
┌────────────────────────── Хост ──────────────────────────┐
│ InputMap → локальные команды                             │
│ Сеть → команды остальных игроков → очереди по игрокам    │
│                         ↓                                │
│ RunSimulation: фиксированный такт 60 Гц                  │
│ команды → отряды → AI → физика/хиты → комната/RNG → итог │
│                         ↓                                │
│ Snapshot + события → EOS P2P → клиенты                   │
└──────────────────────────────────────────────────────────┘

┌────────────────────────── Клиент ────────────────────────┐
│ InputMap → InputFrame → предсказание своего отряда       │
│                    └→ InputBatch → EOS P2P → хост        │
│ Snapshot → reconciliation своего отряда                  │
│ Snapshot → буфер интерполяции чужих актёров и врагов     │
│ ReplicaWorld → только отображение, без игровых решений   │
└──────────────────────────────────────────────────────────┘
```

Одиночный забег использует тот же `RunSimulation` и локальный источник команд. Сетевые классы не должны становиться обязательными для боевого ядра.

### 3.2 Границы модулей

Названия ниже обозначают ответственность, а не обязательный окончательный список файлов.

| Модуль | Ответственность |
|---|---|
| `RunSimulation` | Единый порядок фиксированных тактов и всё авторитетное состояние забега |
| `InputFrame` / `InputBatch` | Данные команды, без ссылок на `Input`, узлы сцены и `Resource` |
| `ActorIdAllocator` | Стабильные уникальные ID героев, врагов, атак, снарядов и лута в пределах забега |
| `RunConfig` | Версия контента, seed, биом, сложность, состав игроков и их отрядов |
| `HostSession` | Приём и проверка команд, симуляция, рассылка состояния, жизненный цикл сессии |
| `ClientSession` | Отправка ввода, предсказание, reconciliation, запрос повторной синхронизации |
| `ReplicaWorld` | Создание и удаление view по ID, интерполяция, применение снапшотов |
| `NetworkTransport` | Отправка пакетов конкретному пиру, надёжность, подключение и отключение |
| `EosTransport` | Реализация поверх выбранного EOS-плагина |
| `LoopbackTransport` | Локальная связь без EOS для одиночной игры и автотестов |
| `SimulatedTransport` | Задержка, джиттер, потери, дубли и переупорядочивание для тестов |

`RunSimulation` не импортирует EOS и не вызывает `Input`. Транспорт не знает правила урона. View не отправляет сетевые сообщения и не меняет авторитетное HP.

## 4. Тактовая модель и ввод

### 4.1 Порядок такта хоста

Базовая частота остаётся **60 Гц**. Порядок фиксируется явно, а не зависит от случайного порядка `_physics_process` узлов:

1. Принять новые пакеты в очереди; не выполнять команды прямо из сетевого callback.
2. Выбрать по одному следующему `InputFrame` на игрока в установленном порядке слотов.
3. Применить команды отрядов и продвинуть `PartyController`.
4. Продвинуть AI и движение врагов.
5. Разрешить физические перемещения, хитбоксы и попадания через общий `DamageSystem`.
6. Обработать смерти, спавн/деспавн, переходы комнат и игровые события.
7. Увеличить `simulation_tick`; каждые три такта сформировать снапшот.

Сетевой callback только валидирует envelope и ставит данные в очередь. Это исключает реентерабельность и применение пакета посередине физического такта.

### 4.2 Формат ввода

`InputFrame` содержит:

- `sequence: uint32` — монотонный номер в пределах сессии игрока;
- `move: Vector2` — нормализованное намерение движения, в протоколе квантуется;
- `pressed: bitmask` — attack, skill, dash, swap 1/2/3, next/prev, interact;
- при необходимости `target_id` для interaction, но не для атаки или урона.

Клиент сэмплирует ввод на каждом своём физическом такте. Пакет `InputBatch` отправляется 30 раз/с и содержит новые кадры плюс ограниченное число предыдущих. Повтор защищает edge-команды от потери одного UDP/P2P-пакета.

Правила хоста:

- identity игрока определяется по EOS-соединению, а не по присланному `player_id`;
- каждый `sequence` исполняется не более одного раза;
- слишком старые, дублирующиеся и превышающие лимит очереди кадры отбрасываются;
- хост сам выбирает такт исполнения и никогда не исполняет команду «в прошлом»;
- при временном отсутствии ввода сохраняется последнее направление движения, но одноразовые действия не повторяются;
- после заданного таймаута направление сбрасывается в ноль;
- очередь ограничена, поэтому клиент не может накопить и мгновенно выполнить сотню атак.

Стартовые параметры для прототипа: отправка 30 Гц, повтор до 12 кадров, очередь не более 250 мс, нейтральный ввод после 250 мс тишины. Это настройки для плейтеста, не константы протокола.

## 5. Синхронизация состояния

### 5.1 Что отправляется

Хост рассылает полный динамический снапшот текущей комнаты **20 раз/с**. Для первой версии полнота важнее экономии трафика: любой новый снапшот можно применить без предыдущего.

`Snapshot` содержит:

- `protocol_version`, `session_id`, `simulation_tick`;
- `room_id` и монотонный `room_revision`;
- `ack_input_sequence` только для получателя;
- активных героев: `actor_id`, владельца, позицию в метрах, facing, действие и уровень рельефа;
- состояние всех трёх героев каждого игрока: HP, alive, active slot, кулдауны и статусы;
- врагов и снаряды: `actor_id`, definition ID, позицию, состояние AI/телеграфа, HP и статусы;
- игровые объекты текущей комнаты и видимый каждому игроку лут.

Статические `.tres` по сети не передаются. Передаются строковые или числовые ID, по которым клиент берёт данные из своей проверенной версии контента.

### 5.2 События и каналы

| Тип данных | Доставка | Источник истины при потере |
|---|---|---|
| Ввод | Ненадёжный, с повтором последних кадров | Следующий `InputBatch` |
| Позиции, HP, кулдауны, статусы, AI | Ненадёжный снапшот | Следующий полный снапшот |
| Spawn/despawn, начало и конец комнаты/забега | Надёжный упорядоченный event | Повторная полная синхронизация |
| Создание/подбор лута, смерть/воскрешение | Надёжный event + состояние снапшота | Снапшот и `Resync` |
| Косметический удар, звук, частицы | Может быть ненадёжным | HP остаётся истиной; потерянный VFX допустим |

У каждого надёжного события есть `event_id`, чтобы повторная доставка не создала второй предмет или не завершила забег дважды. Если снапшот ссылается на неизвестный `actor_id`, view не создаёт объект по догадке: клиент ждёт spawn или просит `Resync`.

После измерения трафика можно перейти к дельтам от подтверждённого базового снапшота. До появления сотен снарядов и реальных замеров оптимизацию не вводить.

### 5.3 Идентификаторы и версии

- ID выделяет только хост. Текущий статический счётчик `BasicEnemy` в сетевой игре не используется.
- `actor_id` не переиспользуется в пределах забега; `attack_instance_id` уникален среди атак.
- `session_id` отсекает пакеты старой сессии; `room_revision` — пакеты предыдущего входа в комнату.
- В handshake входят версия протокола, версия сборки и хеш манифеста геймплейного контента. Несовместимая версия получает понятный отказ до входа в забег.
- `protocol_version` меняется при несовместимом изменении сообщений. Сохранение совместимости «на всякий случай» не требуется, пока все клиенты проходят обязательное обновление.

## 6. Предсказание и отображение

### 6.1 Собственный отряд

Клиент хранит историю неподтверждённых `InputFrame`. На снапшоте он:

1. читает `ack_input_sequence` и авторитетное состояние последнего снапшота;
2. удаляет подтверждённые команды из истории;
3. сравнивает предсказанное состояние с авторитетным;
4. при расхождении восстанавливает состояние снапшота и повторно проигрывает только команды с номерами после `ack_input_sequence`;
5. обновляет view до исправленного результата.

Для точного повторного проигрыша снапшот собственного отряда дополнительно содержит остатки таймеров действий, направление рывка, i-frames/hitstop и вынужденное смещение. Набор полей должен закрывать всё состояние, влияющее на следующий предсказанный такт.

Предсказываются движение, рывок, свап, анимации атаки и скилла. Предсказанный удар может показать замах и косметический эффект, но **не создаёт авторитетный урон и не меняет HP**. Только хост создаёт настоящие хитбоксы.

Небольшую ошибку позиции view сглаживает. Телепорт, смена комнаты, смерть, свап и большое расхождение применяются сразу, без длинного визуального «долёта». Пороги подбираются плейтестом и живут в конфигурации.

На хосте собственный отряд идёт напрямую через симуляцию, без искусственной задержки и prediction/reconciliation.

### 6.2 Чужие актёры и враги

Клиент хранит буфер снапшотов и рисует чужих актёров примерно на **100 мс позже хоста**, интерполируя между двумя состояниями. При длительном отсутствии пакетов разрешена только короткая экстраполяция движения; затем актёр останавливается на последнем известном состоянии. Экстраполировать атаки, смерть и переходы комнат нельзя.

Remote view — обычные `Node2D` без gameplay-коллизий, `Hurtbox2D` и работающего AI. Телеграф строится по авторитетному состоянию и такту. `room_revision` меняется — интерполяция сбрасывается и объекты ставятся в новую комнату сразу.

## 7. Забег и комнаты

### 7.1 Создание

1. Клиенты входят через EOS Connect и получают профиль из Rust API.
2. Хост создаёт EOS Lobby с режимом, сложностью, числом мест, версией протокола и хешем контента.
3. Игроки присоединяются по приглашению и передают выбранный состав отряда.
4. Хост фиксирует состав сессии и `RunConfig`, выделяет слоты и actor ID, создаёт seed.
5. Каждый клиент загружает биом и генерирует геометрию по `run_seed`, затем отправляет `Ready`.
6. Хост начинает забег после готовности всех. При таймауте неготовый игрок исключается до старта либо старт отменяется; автоматический запуск без загруженной комнаты запрещён.

`DungeonGenerator` уже воспроизводит данж по seed и конфигу. Нужен тест одинакового checksum графа и карт на всех целевых платформах. Боевой RNG по seed между клиентами не синхронизируется: его выполняет только хост. Косметика использует отдельный RNG и никогда не влияет на игровой.

### 7.2 Переходы

В MVP все игроки находятся в одной комнате. Хост владеет текущим `room_id`; клиент не переходит сам по факту касания двери.

Последовательность:

1. Хост выбирает переход по игровому правилу и отправляет надёжный `RoomPrepare(room_id, room_revision)`.
2. Хост останавливает старую комнату, очищает старые хитбоксы, AI и очереди edge-команд.
3. Клиент загружает геометрию и отвечает `RoomReady` с тем же revision.
4. Хост расставляет отряды, спавнит врагов и после готовности всех включает симуляцию новой комнаты.
5. HP, смерть героев и кулдауны сохраняются; позиции и временные атаки комнаты пересоздаются.

Для сетевого прототипа переход инициирует хост. Окончательное правило — голосование, все у двери или только хост — относится к дизайну и не зашивается в транспорт.

### 7.3 Отключения в MVP

- Потеря связи с клиентом: хост сначала сбрасывает его ввод, затем по таймауту убирает отряд из симуляции и продолжает забег остальным.
- Повторное подключение в середину забега не поддерживается.
- Потеря хоста или завершение им процесса: забег завершается с явным сообщением; миграции нет.
- Потеря связи с Rust API не должна молча превращаться в локальное сохранение. Итог остаётся незавершённым, показывается ошибка и предлагается повторная отправка.

Эти правила сознательно просты. Если rejoin станет обязательным, он строится через полный snapshot + `RunConfig` + надёжный журнал текущих объектов, а не через попытку восстановить состояние из старых пакетов.

## 8. Лут, итог и серверный API

Лут каждого игрока создаёт хост и помечает `owner_player_id`. Клиент отправляет `InteractRequest(loot_id)`; хост проверяет владельца, живого активного героя, комнату, дистанцию и то, что предмет ещё существует.

После забега:

1. Хост формирует отдельный `RunResult` для каждого игрока и надёжно передаёт его владельцу.
2. Владелец отправляет свой результат в Rust API со своей авторизацией.
3. Ключ идемпотентности — `(account_id, run_id)`; повтор не начисляет награду второй раз.
4. Хост не может записать результат в чужой аккаунт.
5. API не проверяет правдоподобие обычного лута — это согласуется с GDD. Донатная валюта, покупки и гача скинов остаются отдельными серверными операциями.

До реализации этапа 4 сетевой прототип использует фиксированные тестовые отряды и не сохраняет результат. Не нужно ради сетевого боя раньше времени создавать всю мета-прогрессию.

## 9. Изменения текущего кода перед подключением EOS

Это подготовительный рефакторинг без изменения одиночных правил.

1. **Ввести командную границу.** `HeroInputNode` перестаёт напрямую дергать методы и тикать отряд. Он производит `InputFrame`; отдельный планировщик передаёт его в `PartyController` и вызывает `tick()`.
2. **Собрать единый владелец такта.** Перевести врагов и хитбоксы с независимых `_physics_process` на явный порядок симуляции либо управляемый адаптер. Сетевые пакеты не исполняются между их фазами.
3. **Разделить sim и view.** `CombatHeroView` с коллизиями остаётся только на авторитетном хосте. На клиенте используется view без обратной записи позиции в контроллер.
4. **Назначать ID из сессии.** Убрать зависимость от `BasicEnemy._next_actor_serial`; атаки и все актёры получают ID от владельца забега.
5. **Сделать AI многопользовательским.** Заменить единственный `_hero`/`HeroProxy` на список активных героев и детерминированное правило выбора цели на хосте. При свапе и смерти цель пересчитывается.
6. **Вынести жизненный цикл комнаты.** Создание/уничтожение отрядов, врагов, хитбоксов и лута выполняет `RunSimulation`, а не сетевые callbacks и не view.
7. **Сохранить одиночный путь.** Те же команды проходят через локальный источник без сериализации; существующие боевые тесты продолжают проверять правила.

Не требуется переписывать боевую математику или делать её кроссплатформенно детерминированной: вычисляет её только хост.

## 10. План внедрения

### M0. Принятие дизайна и технический spike EOS

- Согласовать host-authoritative модель и ограничения MVP.
- Проверить выбранный community-плагин: Godot 4.7, EOS Connect, Lobby, P2P, relay, reliable/unreliable пакеты, идентичность отправителя, размер сообщения, работу двух экземпляров и целевые платформы.
- Не строить gameplay на API плагина до появления `NetworkTransport`-адаптера.

**Готово:** две тестовые учётные записи обмениваются пакетами напрямую и через relay; ограничения плагина записаны, интерфейс адаптера покрывает их без обходных заглушек.

### M1. Сетенезависимый рефакторинг

**Прогресс:** командная граница реализована — `HeroInputNode` производит `HeroInputFrame`, а `dungeon_preview` отдельно применяет его через `PartyController.apply_input()` и вызывает `tick()`. Враги и хитбоксы переведены с автономного `_physics_process` на явные `BasicEnemy.tick()` и `Hitbox2D.tick()`; порядок preview: ввод (−20) → отряды → враги → попадания (0) → view (1). `ActorIdAllocator` выдаёт ID отрядов и врагов до регистрации в `DamageSystem`; статический счётчик `BasicEnemy` удалён. AI принимает список героев и каждый такт выбирает ближайшую видимую живую цель с tie-break по `actor_id`. Добавлен `RemoteHeroView` на `Node2D` без gameplay-коллизий, хёртбокса и обратной записи в контроллер.

- Команды, единый такт, ID, multi-target AI, отделение remote view.
- Одиночная игра и текущие тесты сохраняют поведение.

**Готово:** одиночный бой проходит прежний сценарий; те же записанные команды дают тот же результат на одном хосте; существующие тесты зелёные.

### M2. Два игрока без EOS

**Прогресс:** добавлены `NetworkTransport` и двухточечный `LoopbackTransport` с `PackedByteArray`, явным `poll()`, адресацией, копированием пакетов и отложенными connect/disconnect-событиями. Покрытие — `test_loopback_transport.gd`. `HandshakeCodec` реализует `CLIENT_HELLO` (protocol/build/content), `HOST_WELCOME` (session/slot) и `REJECT`; malformed/truncated/oversized-пакеты отклоняются. `HostSession` и `ClientSession` проверяют совместимость, выдают слоты 1–3 и обрабатывают повторный hello/disconnect; интеграционный путь покрыт `test_session_handshake.gd`.

- `LoopbackTransport`, handshake, ввод, снапшоты, spawn/despawn, общая комната.
- Два отдельных процесса Godot: хост и клиент, по отряду на каждого.
- Сначала без prediction, чтобы проверить авторитетность и протокол.

**Готово:** клиент управляет только своим отрядом, видит героя хоста и врагов; только хост меняет HP; один удар не наносится дважды; смерть и свап совпадают на обеих сторонах.

### M3. Качество движения и устойчивость

- Prediction/reconciliation собственного отряда, интерполяция остальных.
- `SimulatedTransport`, resync, таймауты, переходы комнат, расширение до четырёх игроков.

**Готово:** при задержке, джиттере и потерях нет дублей действий и объектов; состояние сходится после потерь; четыре игрока проходят несколько комнат.

### M4. EOS и настоящие машины

- Connect, Lobby, приглашения, P2P/relay, проверка версий, понятные ошибки.
- Два игрока на разных машинах и аккаунтах, затем кроссплатформенная проверка доступных платформ.

**Готово:** выполнен критерий сетевой части roadmap — два игрока на разных машинах вместе проходят забег; relay-путь проверен отдельно.

### M5. Правила полного забега

- Персональный лут, перенос тела и воскрешение, скейлинг сложности, итоги и серверное сохранение.
- Здесь закрываются вопросы 121 и 127; сетевой каркас от них не зависит.

**Готово:** награды каждого игрока сохраняются один раз и видны после повторного входа с другой платформы.

## 11. Проверка

### Автотесты

- Кодек: round-trip всех сообщений, отказ на truncated/oversized/unknown-version пакетах, запрет десериализации произвольных объектов Godot.
- Ввод: дубли, пропуски, переупорядочивание, переполнение очереди, нейтральный ввод по таймауту.
- Авторитетность: клиентский пакет не может задать позицию, HP, урон, definition ID или чужой `player_id`.
- События: повтор `event_id` и повтор `RunResult` ничего не дублируют.
- Бой: два/четыре отряда на общем `DamageSystem`, атрибуция DoT, i-frames, свап, смерть, выбор цели AI.
- Комнаты: старые пакеты отбрасываются по `room_revision`, HP/кулдауны сохраняются, хитбоксы старой комнаты не наносят урон.
- Снапшоты: применение без предыдущего, resync после неизвестного актёра, корректный despawn.

### Сетевые сценарии

Прогонять на двух отдельных процессах и перед M4 на двух машинах:

| Условие | Что проверить |
|---|---|
| 50–100 мс RTT, небольшой джиттер | Отзывчивость своего героя и плавность остальных |
| 200 мс RTT, джиттер, 1–5% потерь | Нет дублей, управление восстанавливается, снапшоты сходятся |
| Обрыв и возврат транспорта | Нейтральный ввод, корректное исключение, отсутствие «застывшей» атаки |
| Выход клиента | Остальные продолжают, его объекты удалены |
| Выход хоста | Все получают явное завершение, ложной сохранённой награды нет |
| 4 игрока и плотный бой | CPU хоста, очередь ввода, трафик, время кадра и отсутствие роста памяти |

Конкретный бюджет трафика и максимально допустимую поправку предсказания установить после первых замеров и плейтеста, а не выбрать произвольно сейчас. Ощущение боя на задержке обязательно проверяет человек.

## 12. Безопасность протокола

Даже без серверного античита нужна защита от случайных и намеренно malformed-пакетов:

- строгий allowlist типов сообщений, никаких произвольных Godot RPC по `NodePath`;
- явный бинарный кодек с проверкой длины и диапазонов; не использовать десериализацию объектов из сети;
- лимит пакетов/с, кадров в batch, актёров и событий;
- проверка отправителя по EOS identity и его права на конкретный отряд;
- отказ на NaN и бесконечности, нормализация и ограничение длины вектора;
- никаких путей к ресурсам от клиента — только ID известного контента;
- ошибки протокола логируются без токенов, квитанций и персональных данных.

Это защита стабильности сессии, а не обещание честного хоста. Доверенным хоста для обычных ресурсов делает принятая модель игры.
