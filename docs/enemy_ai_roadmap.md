# Roadmap реализации ИИ врагов

**Дата:** 2026-11-08. **Статус:** R0–R2 завершены. Следующий этап — R3. Состояние каждого этапа отмечено ниже; групповые системы ещё не внедрены.

Цель — группа из 5–10 мобов с твёрдыми телами, доступными позициями атаки, очередями в тесноте и согласованным освобождением пути союзнику, способному достать героя. Данные AI обрабатываются системами, физика и представление остаются в Godot.

Источники требований: [текущее поведение](enemy_ai.md), [целевая архитектура](enemy_ai_architecture.md), [групповой ИИ и границы ECS](enemy_group_ai.md), [соглашения об единицах](conventions.md). Этот файл задаёт последовательность поставок и критерии их закрытия; детали поведения остаются в спецификациях. Он детализирует шаги A–H архитектуры и этапы 1–4 группового дизайна.

## Исходная точка

На старте R0 проверены `src/enemies/`, интеграция в `scenes/debug/dungeon_preview.gd` и существующие тесты:

- `BasicEnemy` совмещает выбор цели, FSM, навигацию, движение, удар и отображение. Состояния — `IDLE`, `CHASE`, `TELEGRAPH`, `COOLDOWN`.
- `RoomNavigation`, боевые состояния, общий `DamageSystem`, hurtbox врага и уникальные `actor_id` уже существуют.
- В preview задано 3 одинаковых врага на комнату. `avoidance_enabled = false`, `collision_layer = 0`: столкновения между врагами отсутствуют.
- Прямая видимость через геометрию, память, возврат, фазовый такт, feedback движения, резервы и групповой планировщик пока отсутствуют.
- Часть исходников и документации не отслеживается Git, есть изменения рабочей копии. Доступность этих файлов здесь не означает, что новый checkout из текущего коммита содержит воспроизводимую базу.

## Порядок и правила выполнения

Основная последовательность: **R0 → R1 → R2 → R3 → R4 → R5 → R6 → R7 → R8 → R9 → R10**. Подготовку тестовых сценариев следующего этапа можно вести раньше; игровое включение требует прохождения зависимостей.

- Каждый этап разбивается на небольшие проверяемые поставки. Статус меняется после проверки результата, а не после создания файлов с нужными именами.
- При выделении компонентов сохраняются нынешние числа и тайминги. Изменения правил вводятся отдельно с тестами нового поведения.
- `ActorIdAllocator` остаётся источником ID, `CombatantState` — владельцем HP и боевых статусов. Повторный тик боевых состояний и второй владелец позиции запрещены.
- Конфигурация хранит метры и секунды; runtime использует фиксированные такты 60 Гц. Общие ресурсы не содержат состояние конкретного моба.
- Удаление, смерть, переход комнаты и очистка новых данных проверяются на каждом этапе. R9 добавляет сквозную проверку всего жизненного цикла, а не откладывает очистку до конца.
- Новые пути и имена тестов ниже — предложения; при реализации использовать существующий эквивалент, если он уже появился. Универсальный ECS-фреймворк и перенос всей игры на ECS не являются зависимостями.

## R3. Восприятие, память и безопасная атака

**Статус:** [ ] не начат. **Зависимости:** R2. **Соответствие архитектуре:** D.

**Работа:** добавить обнаружение с прямой видимостью до 8 м, удержание выбранной цели до 10 м, память последней замеченной позиции на 2 с, `SEARCH` и `RETURN`. **Критерий закрытия:** скрытая текущая позиция героя не попадает в навигацию или будущий координатор. Наблюдения и условия атаки дают проверяемые факты для групповых решений. Правило блокировки ближнего удара союзником пока остаётся рабочим предложением из групповой спецификации; его окончательная политика и тесты определяются до включения R6, без автоматического распространения на снаряды/AoE.

## R7. Очереди и резервирование проходов

**Статус:** [ ] не начат. **Зависимости:** R6. **Соответствие архитектуре:** развитие F.

**Работа:** выделять конфликтующие участки движения и резервировать проход. Назначать позиции ожидания перед тесным участком, сохранять направление активного потока до освобождения участка. Приоритет пригодных участников — по длительности ожидания, затем ID. Резервы имеют срок и проверку продвижения; циклическое ожидание выявляется, без места для отхода допускается ограниченное устойчивое ожидание.

**Проверки:** координатор и физическая группа: дверь, одноклеточный мост, встречные потоки с местами разъезда и без них, оглушённый участник, долго ожидающий моб, обратный порядок входного массива.

**Критерий закрытия:** при доступной геометрии очередь продвигается; при физической невозможности разъезда не возникают пересечения или дрожание. Таймаут уступания различим с `NO_PATH`, перепланировка не обнуляет возраст ожидания и общий бюджет манёвра.

## R8. Согласованное перестроение по возможности атаки

**Статус:** [ ] не начат. **Зависимости:** R7. **Соответствие архитектуре:** развитие F, основной пользовательский сценарий.

**Работа:** при подтверждённой бесполезной блокировке выбрать союзника, который сможет попасть из освобождаемой позиции. Атомарно зарезервировать место атаки, коридор и конечные позиции отхода; построить зависимости уступания. Выполнять план «освободить → пропустить → закрепить», продвигаясь по фактическому результату движения. В одной конфликтующей области активен один план; независимые планы могут выполняться параллельно.

**Проверки:** сначала два моба разной дальности, затем цепочка из 5 и 10: герой в углу, короткая дальность впереди, подходящий атакующий сзади. Проверить неготовую атаку, стену, другой уровень, цепь блокирующих, цикл зависимостей, отсутствие конечного места, замах и стан, смену цели/свап, смерть, движение героя и общий таймаут.

**Критерий закрытия:** группа расступается, выбранный моб получает доступную позицию и возможность удара. Большая дальность сама по себе не даёт приоритет. Несостоявшийся план освобождает все резервы; отменённое задание не исполняется позже, а повторная попытка имеет ограниченный интервал.

## R9. Сквозной жизненный цикл и отмена

**Статус:** [ ] не начат. **Зависимости:** R8. **Соответствие архитектуре:** G.

**Работа:** проверить совместную очистку компонентов, путей, карт/RID, заданий, резервов, атак и регистрации бойцов. Пространственные вторичные попадания получают контекст комнаты и отмену по epoch, при сохранении существующих правил статусов отряда и атрибуции DoT.

**Критерий закрытия:** события старого epoch не меняют новую комнату. В реестрах остаются только актуальные участники, повторная очистка безопасна, текущие правила боевого ядра не нарушены.

## Проверки и фиксация результатов

При первом запуске в новом checkout подготовить импорт:

```bash
godot --headless --editor --import --path . --quit
```

Существующая базовая регрессия из корня проекта:

```bash
godot --headless --fixed-fps 60 --path . -s res://tests/test_basic_enemy.gd
godot --headless --path . -s res://tests/test_room_navigation.gd -- --seeds=3
godot --headless --fixed-fps 60 --path . -s res://tests/test_combat_preview.gd
godot --headless --path . -s res://tests/test_damage_system.gd
godot --headless --path . -s res://tests/test_actor_id_allocator.gd
```

Ожидается exit code 0 и `ALL PASSED` у каждой проверки. Навигацию запускать без `--fixed-fps`, с ожиданием реальной готовности сервера и ограничением времени. Тесты R1/R2 уже созданы; тесты последующих этапов и их команды добавляются по мере реализации. Проверки чистых данных не требуют рендера, физические сценарии исполняются фиксированными тактами и проверяют инварианты с измеренными допусками.

Дополнения R1/R2 и затронутая регрессия героев/попаданий (вместе с пятью базовыми командами — 12 проверок):

Отчёт каждой поставки содержит ревизию/коммит, закрываемый пункт, выполненные команды и результат, фактические изменения поведения и оставшиеся ограничения. Для нетривиального исправления тест должен воспроизводить ошибку без исправления. Полный набор проверок расширяется только тестами уже реализованных этапов.
